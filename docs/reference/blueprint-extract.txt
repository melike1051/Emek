0. Yönetici Özeti
Emek, ev içi ve bakım hizmetlerinde müşteri ile bağımsız kadın hizmet sağlayıcıları bir araya getiren iki taraflı bir
dijital pazar yeri olarak tasarlanmıştır. Teknik olarak ürünün basit bir ilan/listeme uygulaması olmaması; doğal dil
işleme, akıllı eşleştirme, çok kriterli optimizasyon, rota planlama, hizmet oturumu bazlı güvenlik telemetrisi, dijital
ispat, şartlı ödeme orkestrasyonu ve ölçülebilir veri analitiği katmanlarını tek bir platformda birleştirmesi
hedeflenmektedir.
Temel mimari kararı: mobil uygulama Flutter/Dart, web Next.js/TypeScript, ana backend NestJS/TypeScript,
AI/ML/optimizasyon Python, ana veri PostgreSQL + PostGIS, cache/lock Redis, asenkron event altyapısı Google Pub/Sub,
compute Cloud Run ve yönetilen Google Cloud bileşenleridir.
En kritik tasarım ilkesi: teknoloji yalnızca “güncel görünsün” diye eklenmemeli; her bileşen somut bir ürün veya Ar-Ge
problemini çözmelidir. Bu nedenle Kubernetes, aşırı mikroservisleşme veya her şeyi Python ile yapma yaklaşımı
başlangıçta önerilmemektedir. Buna karşılık NLP, matching, optimization ve anomaly detection için Python ayrı servis
alanı olarak kullanılmalıdır.
TÜBİTAK açısından güçlü anlatım, “en fazla teknoloji ismini kullanmak” değil; belirli teknolojik belirsizlikleri deneysel
olarak çözmek, ölçmek ve sürümler arasında karşılaştırmaktır. Bu nedenle NLP, eşleştirme/optimizasyon,
güvenlik/anomali ve gerçek zamanlı düşük gecikmeli platform çalışması temel Ar-Ge eksenleridir.


1. Projenin Teknik Olarak Yeniden Çerçevelenmesi
Emek’i yalnızca “Armut benzeri bir hizmet uygulaması” olarak tanımlamak yerine aşağıdaki dört katmanın birleşimi
olarak ele almak önerilmektedir:
      Marketplace Platformu: müşteri, sağlayıcı, hizmet, müsaitlik, rezervasyon, ödeme, yorum ve uyuşmazlık yönetimi.
      AI / Decision Engine: doğal dil talebi yapılandırma, aday sağlayıcı çıkarımı, puanlama, çok kriterli eşleştirme ve
       optimizasyon.
      Safety & Digital Proof: hizmet oturumu bazlı geofencing, telemetri, anomali skoru, panic flow, check-in/out ve
       Before/After kanıtları.
      Cloud-Native Operations: event-driven mimari, cache, gözlemlenebilirlik, güvenlik, CI/CD ve analitik.
Önerilen üst düzey cümle: “Emek; doğal dil tabanlı hizmet taleplerini yapılandırılmış iş kısıtlarına dönüştüren yapay
zekâ katmanı ile coğrafi konum, zaman penceresi, yetkinlik, sağlayıcı kapasitesi, geçmiş performans ve güvenlik
değişkenlerini birlikte değerlendiren çok kriterli optimizasyon çekirdeğini; mobil telemetri ve geofencing tabanlı
güvenlik mekanizmaları ile olay güdümlü cloud-native altyapı üzerinde birleştiren iki taraflı dijital hizmet pazaryeri
platformudur.”

Tek kişinin iki ayrı e-posta/telefonla ikinci hesap açmasını engellemek için doğrulanmış kimlik referansı üzerinde
veritabanı seviyesinde UNIQUE kısıtı kullanılmalıdır. Bu kısıt yalnızca uygulama koduna değil, doğrudan veritabanına
konmalıdır; yarış koşullarında bile mükerrer kaydı son savunma olarak engeller.
Önerilen model: “1 kişi = 1 User”. Aynı User altında Customer Profile ve Provider Profile bulunabilir. Böylece aynı
kişinin farklı roller için iki farklı hesabı oluşmaz.
Ham T.C. kimlik numarasını platformun tüm tablolarında dolaştırmak yerine mümkün olduğunda yetkili doğrulama
sağlayıcısının subject/reference değeri veya gizli anahtarlı deterministik HMAC tabanlı identity_hash kullanılabilir. Bu,
veri minimizasyonuna yardımcı olur; ancak tek başına KVKK yükümlülüklerini ortadan kaldırmaz.


8. Önerilen PostgreSQL DDL (Başlangıç Şeması)
-- Extensions
CREATE EXTENSION IF NOT EXISTS pgcrypto;
CREATE EXTENSION IF NOT EXISTS postgis;

CREATE TYPE user_status AS ENUM ('PENDING','ACTIVE','SUSPENDED','DELETED');
CREATE TYPE app_role AS ENUM ('CUSTOMER','PROVIDER','ADMIN','SUPPORT');
CREATE TYPE verification_status AS ENUM ('PENDING','VERIFIED','REJECTED','EXPIRED');
CREATE TYPE verification_level AS ENUM
('UNVERIFIED','PHONE_VERIFIED','IDENTITY_VERIFIED','PROVIDER_VERIFIED','FULLY_VERIFIED');

CREATE TABLE users (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    phone VARCHAR(32),
    email VARCHAR(320),
    status user_status NOT NULL DEFAULT 'PENDING',
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    last_login_at TIMESTAMPTZ
);
CREATE UNIQUE INDEX uq_users_email ON users (lower(email)) WHERE email IS NOT NULL;
CREATE UNIQUE INDEX uq_users_phone ON users (phone) WHERE phone IS NOT NULL;

CREATE TABLE user_roles (
    user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    role app_role NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (user_id, role)
);

CREATE TABLE customer_profiles (
    user_id UUID PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
    display_name VARCHAR(120),
    preferences JSONB NOT NULL DEFAULT '{}'::jsonb,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE provider_profiles (
    user_id UUID PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
    display_name VARCHAR(120),
    bio TEXT,
    experience_years NUMERIC(4,1),
    rating_avg NUMERIC(4,2),
    rating_count INTEGER NOT NULL DEFAULT 0,
    quality_score NUMERIC(6,4),
    verification_status verification_status NOT NULL DEFAULT 'PENDING',
    active BOOLEAN NOT NULL DEFAULT FALSE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()

CREATE TABLE identity_records (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),

    verified_at TIMESTAMPTZ,

    UNIQUE (verification_provider, provider_subject_id),
    UNIQUE (identity_hash)
);

10. Kimlik Doğrulama, NFC/e-ID, EKDS ve Multi-Account Prevention
NFC/e-ID fikrinin temel mantığı uygundur: kullanıcı uygulamada kimlik doğrulamayı başlatır, uygun cihaz
özellikleriyle kart üzerindeki elektronik bilgileri ve/veya yetkili bir kimlik doğrulama hizmetini kullanarak doğrulama
yapılır; doğrulama sonucunun bir benzersiz referansı Emek identity kaydına bağlanır.
Ancak NFC’nin tek başına “telefonu tutan kişi = kart sahibi” sonucunu garanti etmediği unutulmamalıdır. Daha yüksek
güven seviyesinde identity provider’ın sunduğu ek doğrulamalar (ör. canlılık/yüz eşleştirme) değerlendirilebilir.
Biyometrik veriler devreye girdiğinde KVKK açısından çok daha sıkı kurallar oluşur.
EKDS/KDHS erişimi veya resmi veri kaynaklarına doğrudan bağlanma varsayımı yerine bir Identity Verification
Adapter Layer kurulması önerilir. Böylece yetkili bir servis, e-ID/NFC çözümü veya ticari KYC sağlayıcısı değiştiğinde
core backend değişmez. Erişilebilen yöntem ve izinler başvuru ve uygulama öncesinde ilgili kurum/sağlayıcılarla
doğrulanmalıdır.

25. Mimari Kararların Gerekçeleri
Neden NestJS? Web ve backend tarafında TypeScript ortaklığı, modüler controller/service yapısı, validation,
event/queue entegrasyonu ve ekip geliştirme hızını destekler. Next.js ile aynı dil ailesi kullanılır.
Neden Python sadece gerektiği yerde? NLP, ML, OR-Tools ve veri bilimi ekosistemi nedeniyle AI/optimization kısmında
Python doğal avantaj sağlar. Core CRUD/transaction/business logic’i Python’a taşımak zorunlu değildir.
Neden PostgreSQL? Booking, payment, role, availability ve state transition gibi ilişkisel, transaction-sensitive veriler
için güçlü tutarlılık gerekir. PostGIS coğrafi sorguları sağlar.
Neden Cloud Run? Stateless container servisleri için yönetilen, otomatik ölçeklenen ve küçük ekipte operasyon yükünü
azaltan bir compute katmanıdır.
Neden Pub/Sub? Booking/payment/safety eventlerini gevşek bağlı biçimde dağıtarak core request path’ini hafifletir ve
gelecekte servislerin ayrı ölçeklenmesini sağlar.
Neden Kubernetes değil? Başlangıçta operasyonel karmaşıklığı artırır. Gerçek yük ve organizasyon gereksinimi
oluştuğunda değerlendirilebilir.
Neden Firestore sadece yardımcı? Realtime/chat gibi alanlar için hızlı olabilir; ancak finansal ve karmaşık ilişkisel
çekirdekte PostgreSQL daha uygun bir ana sistemdir.
